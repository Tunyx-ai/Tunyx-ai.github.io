Tunyx is a **control plane**, not an engine. It sits between your applications and an inference engine (vLLM,
SGLang, llama.cpp or MLX) and does the work an experienced inference engineer would: choose settings, measure
them, check quality, roll changes out safely and keep everything running.

```txt
plan ─► serve the best config that fits (in seconds if this machine knows the model)
            │
            └─► optimize in the background ─► switch automatically, or propose for your approval
                                                                      │
                     retune from real traffic ◄─ monitor ◄─ serve ◄───┘   (one stable endpoint throughout)
```

<Steps>

1. **Plan.** Detects your hardware (GPUs, MIG slices, Apple Silicon, ROCm, `CUDA_VISIBLE_DEVICES`, busy GPUs)
   and reads the model's configuration without downloading weights. Then it picks the engine, precision,
   tensor-parallel layout, replicas and context length. Context is derived from the memory left after weights,
   never guessed. Run `tunyx plan MODEL` to see the plan and reasons without launching anything.

2. **Serve first.** Starts the highest-fidelity configuration that fits, checks that it answers a real request
   and opens the endpoint. Downtime is only as long as the engine takes to start. If this machine has optimized
   the model before, it starts straight away with the best settings it found then.

3. **Optimize in the background.** A background job benchmarks faster candidates against your
   [workload profile](/docs/concepts/profiles/), with the serving config measured in the same run so the
   comparison is fair. On multi-GPU machines, candidates run in parallel, one per GPU.

4. **Validate.** Each candidate must meet the profile's latency targets and pass every threshold in your
   [quality gate](/docs/concepts/quality-gates/).

5. **Switch or propose.** The winner replaces the serving config only if it's clearly better and statistically
   ahead, not just ahead by noise. By default the switch is automatic, with a canary and automatic rollback. With
   `--manual-apply` it becomes a proposal you approve. If nothing beats the serving config, nothing changes.

6. **Operate.** Restarts crashed engines, puts idle models to sleep, rolls out updates with canary and
   automatic rollback, and proposes retunes as traffic changes.

</Steps>

## One stable endpoint

Applications always call the same URL. Behind it, the gateway:

- resolves the model name to a deployment;
- applies fair admission control: the team with the shortest queue goes first;
- routes to the least-busy healthy replica, with session affinity for agent workloads;
- splits traffic during canaries;
- holds requests briefly while a crashed engine restarts or a sleeping model wakes;
- records latency, tokens and cost for every request.

## The model registry

Each machine remembers what it learned about every model it has optimized: the best configuration, the quality
reference results, and the variants it built. Deleting a deployment keeps this, so deploying the model again
starts optimized in the time it takes the engine to start. Fine-tunes of a known architecture start with its
performance settings. Launch workarounds the machine needed once (for example, no CUDA compiler installed) apply
from the first launch afterwards.

```bash
tunyx registry                 # what this machine remembers
tunyx down NAME --purge        # delete a deployment and forget its model
tunyx registry forget MODEL    # forget one model
```

## Revisions

Every configuration Tunyx serves is a numbered **revision**. Swaps, retunes and re-optimizations create new
revisions; rollbacks return to earlier ones. `tunyx status NAME` shows the history with the outcome of each.

## Crash-safe state

Tunyx keeps its state in a local SQLite database (WAL mode) with hourly backups. If the daemon restarts, it
re-attaches to engines that are still running, after verifying their identity, or relaunches the last good
revision.
