Tunyx works like an inference engineer: get a good base configuration first, then try one optimization technique at
a time, keep only what is measurably faster and still passes every quality check, and undo the rest.

## Modes

| Mode | What it does | When to use |
|---|---|---|
| `quick` | Validates one configuration | Fast iteration, small GPUs |
| `standard` (default) | 3–5 base configurations, then up to 6 optimization techniques | Most deployments |
| `thorough` | 6–10 base configurations, then every applicable technique (up to 30) | Production models that will run for a long time |

```bash
tunyx up MODEL -O thorough
```

The endpoint is live as soon as the first configuration validates. The rest runs in the background. Use
`--wait-optimal` to wait for the full search instead.

## The techniques

| Category | Techniques | Quality risk |
|---|---|---|
| **Precision, applied by the engine** | FP8 per-channel / block-wise / per-tensor; MXFP8 (Blackwell); INT8 weight-only and dynamic NVFP4 for MoE experts | Lossy: always quality-gated |
| **Precision, built by Tunyx** | Calibrated INT4 (GPTQ); INT4 with sensitive layers kept 16-bit; INT8 W8A8 (SmoothQuant + GPTQ); NVFP4 weight-only and NVFP4 W4A4 (Blackwell; W4A4 for 3B+ models) | Lossy: always quality-gated |
| **Memory** | FP8 KV cache; KV-cache offloading to CPU memory for long-context agents | FP8 KV is gated |
| **Speculative decoding** | The model's own MTP heads; published EAGLE-3 heads; an automatically paired small draft model; suffix decoding; n-gram prompt lookup | None: output is identical |
| **Engine runtime** | Performance mode for your workload; async scheduling; maximum compilation (`-O3`); CUDA graphs; alternative attention kernels | None |
| **Batching** | Batch size up or down; prefill chunk size up or down | None |
| **Parallelism** | Expert parallelism and dual-batch overlap for MoE models on several GPUs | None |

Tunyx only tries what applies to your model, engine and hardware. The order follows your workload: speculation first
for `chat`, precision first for `batch`, suffix decoding and KV memory first for `agent`.

## How a technique is judged

1. It runs your workload benchmark and your full [quality suite](/docs/concepts/quality-gates/).
2. It is **kept** only if goodput improves by at least 3% (5% for lossy techniques, which must justify their quality
   risk), and by more than the measurement noise of the two runs (95% confidence), and every threshold still passes. Otherwise it is
   **reverted**. Techniques that can't change outputs (batching, scheduling, compilation) skip the quality suite.
3. Kept techniques stack: the next technique is tried on top of the current best.
4. A lossy technique that breaks a threshold is **stepped back** to the next less aggressive option instead of being
   dropped.

```
INT4 -> INT4 with sensitive layers 16-bit -> INT8 W8A8 -> FP8 per-channel
NVFP4 W4A4 -> NVFP4 weight-only -> MXFP8          (Blackwell)
```

Turn step-back off with `--on-quality-fail reject`.

Every attempt, with its metrics and the reason for the decision, is in the [history report](/docs/guides/history-report/).

## Quantization Tunyx builds itself

For the "built" precisions, Tunyx produces its own quantized model from the original weights with
[llm-compressor](https://github.com/vllm-project/llm-compressor), calibrated on representative conversations. Built
variants are cached per recipe and calibration data, so nothing is built twice, and each records how it was made.

Calibrate on your own traffic for the best results:

```bash
tunyx up MODEL --calibration my_prompts.jsonl   # one {"messages": [...]} per line
```

llm-compressor pins its own library versions, so it gets its own environment. One command sets it up, and Tunyx
finds it automatically:

```bash
tunyx setup quantization     # creates ~/.tunyx/envs/quant-env with llmcompressor
tunyx doctor                 # confirms calibrated quantization is available
```

<Aside>
  Without it, Tunyx still tries every engine-applied precision and skips the built ones. Builds run in their own
  process on the GPU they were given, and a variant is reused only if it came from exactly the same weights,
  recipe, calibration data and toolkit versions. `tunyx artifacts` shows built variants and their disk use;
  `tunyx artifacts gc` deletes unused ones.
</Aside>

## Proof: comparison with stock defaults

In `standard` and `thorough` modes, Tunyx also benchmarks the engine's **untuned defaults** on the same GPU share and
workload, so `tunyx status` shows what tuning bought you:

```txt
Tuned config vs stock engine defaults on this workload: +38% goodput
```

## Background optimization: automatic or manual switching

`tunyx up` serves first and optimizes afterwards. The background job runs only while traffic is light: every
model on the same GPUs below 25% of its measured capacity (`optimize_max_load`), or inside your optimization
window. It pauses if traffic picks up and continues in the next quiet period. When the background job finds a configuration that is clearly
faster and passes every threshold:

- **automatic (default):** Tunyx switches to it with a canary and automatic rollback;
- **manual:** it becomes a proposal with the measured gain, and you decide.

```bash
tunyx up MODEL --manual-apply      # propose instead of switching
tunyx tune NAME --apply manual     # change it later (or --apply auto)
tunyx proposals NAME               # what's waiting
tunyx approve ID                   # apply it (canary + automatic rollback)
```

A proposal expires if the serving configuration changes first. With `TUNYX_REQUIRE_APPROVAL=1`, results are always
proposals.

## Remembered per machine

Results are kept in the machine's [model registry](/docs/concepts/how-it-works/#the-model-registry), and survive
`tunyx down`. Redeploying the same model starts in its best configuration; fine-tunes of the same architecture
start with its performance settings. `--fresh` ignores what's remembered; `tunyx down NAME --purge` forgets it.

## Busy GPUs and the optimize window

Background optimization never takes a busy single-GPU deployment offline for long. When traffic is waiting, the
search is shortened, and a configuration that meets its targets is never replaced by one that doesn't. To allow full
re-optimization during quiet hours:

```bash
tunyx config set optimize_window 02:00-05:00
```
